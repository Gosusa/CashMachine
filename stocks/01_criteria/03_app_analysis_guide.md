# 3. 앱용 분석 파일 작성 가이드

> `02_tickers/{TICKER}/{TICKER}_base.md` 와 `{TICKER}_stress.md` 를 입력으로 받아, 앱 사용자용 분석 파일을 생성하는 변환 규칙.

---

## 목적

- **입력**: `{TICKER}_base.md` (내부 분석용, 상세) + `{TICKER}_stress.md` (스트레스 테스트)
- **출력**: `app/data/{TICKER}/{TICKER}_analysis.md` (앱 사용자용)
- **독자**: 앱 사용자 (투자 판단에 필요한 근거 + 결론)
- **언어**: 한글

---

## 작성 원칙

1. **내용 전량 유지** — base.md와 stress.md의 모든 판단·근거·수치를 포함한다. "상위 N개"로 임의 축소하지 않는다
2. **중복만 제거** — 동일 정보가 복수 섹션에 반복될 때, 가장 완결된 서술 1개로 합친다
3. **근거 있는 결론** — 결론만 적지 않는다. 논리적 사실·수치 근거와 함께 기술한다
4. **모바일 가독성** — 테이블 셀에는 숫자·키워드·판정(✅/⚠️/❌)만 넣는다. 문장 설명은 테이블 아래에 별도 서술하되, **base.md 원본 수준 이상으로 상세히** 기술한다. 테이블 셀 제약 때문에 축약했던 내용을 풀어 쓰는 것이므로, 오히려 base.md보다 맥락·근거·수치가 더 풍부해야 한다
5. **구조적 사실만** — 1년 이상 유효한 구조적 사실만 기술한다. 단기 트렌드·시장 센티먼트 해설은 제외한다

---

## YAML Frontmatter (필수)

파일 최상단에 아래 형식의 YAML frontmatter를 **반드시** 포함한다. DB 업로드 스크립트(`upload_to_db.py`)가 이 블록을 파싱하여 Supabase에 저장한다.

```yaml
---
ticker: AAPL
name: Apple Inc.
sector: Technology
analysis_date: 2026-04-18
thesis_summary: 생태계 전환비용 + 서비스 마진 확장으로 FCF 복리 성장
target_price: 263
extreme_bear_price: 130
bear_price: 180
base_price: 280
bull_price: 457
---
```

**필드 규칙:**

| 필드 | 타입 | 필수 | 설명 |
|------|------|------|------|
| ticker | string | Y | 대문자 티커 |
| name | string | Y | 회사 정식명 (영문) |
| sector | string | Y | 아래 섹터 분류표 참조 |
| analysis_date | string | Y | YYYY-MM-DD 형식 |
| thesis_summary | string | Y | 핵심 투자 논거 한 줄 요약 (50자 이내, 해자 유형 + 성장 동력 중심) |
| target_price | number | Y | 가중평균 내재가치 ($) |
| extreme_bear_price | number | N | Extreme Bear 시나리오 목표가. 없으면 생략 |
| bear_price | number | Y | Bear 시나리오 목표가 |
| base_price | number | Y | Base 시나리오 목표가 |
| bull_price | number | Y | Bull 시나리오 목표가 |

**섹터 분류:**

| 섹터 | 해당 키워드 |
|------|-----------|
| Technology | 소프트웨어, 클라우드, SaaS, AI, 검색, 광고 플랫폼, 스마트폰, 플랫폼 |
| Semiconductor | 파운드리, 장비, 리소그래피, 메모리, DRAM, NAND, HBM, GPU, 반도체 |
| Financial | 금융, 은행, 카드, 결제, 핀테크, 자산운용, 보험 |
| Healthcare | 제약, 바이오, 헬스케어, 의약품, 면역 |
| Consumer | 이커머스, 리테일, 소비재, 소매, 생필품 |
| Energy | 석유, 에너지, 정유, LNG |
| Industrial | 건설, 장비, 중장비, 인프라 |
| Entertainment | 스트리밍, 엔터테인먼트, 숙박, 여행 |

**주의:**
- frontmatter는 파일의 **첫 줄**(`---`)부터 시작해야 한다
- 가격 필드에 `$` 기호를 넣지 않는다 (숫자만)
- target_price는 가중평균 내재가치를 사용한다 (Base 목표가가 아님)
- thesis_summary는 볼드·마크다운 서식 없이 **순수 텍스트**로 작성한다

---

## 파일 구조 (섹션 순서)

frontmatter 바로 아래부터 본문이 시작된다. **섹션 헤더는 아래 형식을 정확히 따른다** — 번호(`1.`, `2.` 등)를 붙이지 않는다.

```
---
(YAML frontmatter)
---

# {TICKER} — {회사 정식명}
> 한 줄 요약
---
## 투자 thesis
## 사업 구조 및 해자
## 경쟁 구도 및 경쟁 우위
## 리스크 요인
## 가치평가
## 종합 판정
## 스트레스 테스트
## 모니터링 지표
```

---

## 변환 규칙 — base.md 섹션 → app 섹션 매핑

| base.md 섹션 | app 섹션 | 변환 |
|---|---|---|
| 투자 thesis | 투자 thesis | 유지 |
| 사업 구조 및 경제적 해자 | 사업 구조 및 해자 | 합침 |
| 해자 팩트체크 | 사업 구조 및 해자 | 합침 |
| 해자 강도 평가 | 사업 구조 및 해자 | 합침 |
| 경쟁 구도 및 경쟁 우위 | 경쟁 구도 및 경쟁 우위 | 유지 |
| 리스크 요인 | 리스크 요인 | 합침 |
| 모니터링 지표 | 모니터링 지표 | 합침 |
| DCF 시나리오 & 가치평가 | 가치평가 | 축약 |
| 종합 판정 | 종합 판정 | 유지 |
| 분기별 점검 기록 | (제외) | — |

| **stress.md 섹션** | **app 섹션** | **변환** |
|---|---|---|
| 시나리오별 스트레스 테스트 | 스트레스 테스트 | 유지 |
| Bear DCF 시뮬레이션 합산 | 스트레스 테스트 | 유지 |
| Bear → Stress 반영 시 비교 | 스트레스 테스트 | 유지 |

각 변환의 상세 규칙은 아래 "섹션별 작성 규칙"에서 정의한다.

### 중복 제거 대상 — base에서 반복되는 정보

| 정보 | base 등장 위치 | app 귀속 섹션 |
|------|--------------|-------------|
| 해자 식별·검증·판정 | 2번, 3번, 4번 | 사업 구조 및 해자 |
| 해자 리스크 (해자 훼손 관점) | 3번, 4번 | 사업 구조 및 해자 |
| 투자 리스크 (투자 영향 관점) | 3번, 4번, 6번 | 리스크 요인 |
| 모니터링 항목 | 7번, 8번 진입신호, 9번 핵심 | 모니터링 지표 |
| 밸류에이션 수치 | 1번, 5-4번, 8-5번, 9번 | 각 섹션에서 1회만 |

## 섹션별 작성 규칙

### 1. 투자 thesis

base 그대로 유지한다.

**포함 항목:**
- 핵심 투자 논거 (해자 유형 + 수치 근거)
- 분석 작성일, 목표가(가중평균 내재가치), 투자 기간

---

### 2. 사업 구조 및 해자

**소스**: base 2번(사업 구조) + 3번(해자 팩트체크) + 4번(해자 강도 평가)

**합치는 원리**: base에서 세그먼트별로 3개 섹션에 걸쳐 기술하는 내용(해자 식별 → 팩트체크 → 강도 평가)을 **세그먼트 단위로 1회에 기술**한다.

**구조:**

#### 2-1. 세그먼트 요약 테이블

base 2-1과 동일하게 가져온다.

| 세그먼트 | 수익원 | 규모 지표 | 해자 유형 | 해자 강도 |
|---------|------|---------|---------|---------|

#### 2-2. 세그먼트별 상세

각 세그먼트마다 `### {세그먼트명}` 형식으로 작성. 아래 내용을 **한 패스로** 기술한다:

**① 사업 구조** — 1~2줄 설명 (base 2-2에서)

**② 해자 유형 테이블** — base 2-2의 해자 테이블에 3번 팩트체크 결과를 "검증" 열로 추가. 해자 유형 열에 핵심 키워드만 괄호로 병기한다.

| 해자 유형 | 검증 |
|---------|------|
| {유형} ({키워드}) | ✅/⚠️/❌ |

테이블 아래에 각 해자의 상세 내용·근거를 서술한다. ⚠️ 또는 ❌ 판정 항목은 반드시 근거를 명시한다. (예: "RDMA 성능 우위는 Oracle 자체 주장 중심이며 독립 벤치마크가 제한적")

**③ 해자 리스크** — base 3번의 세그먼트별 해자 리스크 + 4번의 현실화 시점을 합쳐서 여기에 기술. **"이 리스크가 해자를 훼손하는가"** 관점으로 서술한다. 동일 리스크가 4번 리스크 요인에도 등장할 수 있으나, 여기서는 해자 평가 맥락(훼손 정도 + 현실화 시점)만 다루고, 투자 영향(시나리오 영향, 완화 요인 등)은 4번에서 다룬다

#### 2-3. 해자 강도 판정

base 4번의 판정 블록을 가져온다:
- **최종 판정**: Wide / Narrow / None + 이모지
- **핵심 근거**
- **주의 구간**: Wide 판정이라도 균열을 알려줄 선행 지표

---

### 3. 경쟁 구도 및 경쟁 우위

**소스**: base 5번

base 5번의 4개 서브섹션을 그대로 유지한다:
- 5-1. 경쟁사 식별 및 포지셔닝
- 5-2. 핵심 성장동력 경쟁 비교
- 5-3. 경쟁 우위 원천 분석
- 5-4. 투자 차별화 근거 + 밸류에이션 비교

**모바일 포맷 규칙**:
- 경쟁사 비교 테이블의 셀은 숫자·순위(🥇/🥈)만 넣는다
- 비교 해석(예: "왜 규모 열위에도 투자 가치가 있는가")은 테이블 아래에 서술한다
- 밸류에이션 비교 테이블의 "정당성" 열처럼 문장이 들어가는 열은 제거하고 테이블 아래에 서술한다

---

### 4. 리스크 요인

**소스**: base 3번(해자 리스크) + 4번(리스크 vs 시점) + 6번(리스크 요인)

**합치는 원리**: base 6번의 투자 리스크를 중심으로, 3번·4번에서 투자 영향 관련 정보를 합친다. **"이 리스크가 투자에 얼마나 영향을 주는가"** 관점으로 서술한다. 해자 리스크와 겹치는 항목은 해자 평가(2번)에서 다룬 해자 훼손 관점과 별개로, 여기서는 시나리오 영향·완화 요인·팩트체크를 다룬다.

**중복 합침 예시** — "하이퍼스케일러 자본 경쟁"이 base에서 3번 등장:
- 3번 해자 리스크: "하이퍼스케일러 자본 군비경쟁: MSFT/GOOGL/META/AWS 연 $80~120B"
- 4번 리스크 시점: "하이퍼스케일러 경쟁 | 진행 중 | 해자 훼손 중간"
- 6번 리스크 요인: "4. 하이퍼스케일러 자본 경쟁 심화 ⚠️ — 팩트체크 ✓"

→ app에서는 1개 리스크 항목으로 합쳐서, 설명·수치·시점·영향·팩트체크를 한 번에 기술.

**각 리스크에 포함할 내용:**
- 리스크 설명 + 규모/비중 수치 (base 6번에서)
- 현실화 시점 (base 4번에서)
- 시나리오별 영향 — 어떤 DCF 시나리오에서 현실화되는가 (base 6번에서)
- 완화 요인 (base 6번에서)
- 팩트체크 상태: ⚠️/❓인 항목만 명시 (base 6번에서)

**리스크 독립성**: base 6번의 리스크 독립성 분석을 포함한다. 독립적으로 작동하는 사업/자산이 있으면 명시.

**리스크 수는 base와 동일** — base에 8개 리스크가 있으면 중복 합침 후 남는 고유 리스크 전부 기재. 임의 축소 금지.

---

### 5. 가치평가

**소스**: base 8번 (DCF 시나리오 & 가치평가)

#### 5-1. DCF 방법론

base 8-0의 방법론 선택 블록을 가져온다:
- 적용 방식, 선택 근거, 대안 대비 우위, 주요 가정

#### 5-2. 시나리오 요약 테이블

4개 시나리오를 1개 테이블로 요약한다:

| 시나리오 | 확률 | 목표가 |
|---------|------|-------|
| Extreme Bear | X% | $XX |
| Bear | X% | $XX |
| Base | X% | $XX |
| Bull | X% | $XX |

테이블 아래에 각 시나리오의 **전제 조건** 상세를 서술한다. base 8-2의 전제 조건·완화 요인 등 모든 내용을 포함하되, **계산 코드블록은 제외**한다. 핵심 가정(매출, 마진, EPS, 멀티플)은 서술에 포함.

**Bull 시나리오**: base의 실현 가능성 분석을 그대로 포함한다:
- 전제별 실현 가능성 테이블 (선행 사례/반례 포함)
- 실현 경로 (인과 체인)
- 전제 간 독립성 분석
- 종합 실현 확률 판단

#### 5-3. 가중평균 내재가치

base 8-3의 가중평균 테이블 + 확률 배분 근거를 그대로 가져온다.

#### 5-4. 현재 실적 위치

base 8-4의 내용을 포함한다:
- 직전 실적 테이블 (KPI + DCF Case 위치)
- 트렌드 판단
- 가이던스 반영 시 방향
- 핵심 관찰 (가장 중요한 변수 + 확인 시점)

#### 5-5. 가치평가 결과

base 8-5의 결과 테이블 + 손익비 분석을 가져온다.

**현재가 의존 지표는 제외한다.** Forward PE·PEG 등 시세 기반 지표는 정적 파일 특성상 즉시 stale해지므로 포함하지 않는다. DCF 시나리오 자체의 적용 멀티플(예: "Base PE 18~20x")은 가정이므로 포함.

**손익비는 Base 목표가를 기준으로 산출한다:**
- Bull 업사이드 = Bull 목표가 − Base 목표가
- Bear 다운사이드 = Base 목표가 − Bear 목표가
- 손익비 = Bull 업사이드 ÷ Bear 다운사이드

현재 주가와 무관하게 투자의 상방/하방 비대칭성을 보여주는 구조적 지표.

| 지표 | 수치 | 평가 |
|------|------|------|

"평가" 열에 문장이 길어지는 항목은 테이블에서 짧은 키워드만 넣고, 상세 해석은 테이블 아래에 서술한다.

결론 (핵심 조건부 진술 — "어떤 조건이 달성되면 어느 시나리오가 실현되는가")을 마지막에 기술.

### 6. 종합 판정

**소스**: base 9번

그대로 유지하되, **현재가 참조를 제거**한다:
- 평가 요약 코드블록 (비즈니스 퀄리티, 시장 환경, 가치평가, 리스크, 종합 의견) — 가치평가 판정은 시나리오 비대칭성 기반으로 서술 (현재가 대비 X% 식 표현 금지)
- **"왜 매수가 아닌가"** + **"왜 매도가 아닌가"** (필수) — 구조적 근거 중심. 현재가 vs 내재가치 gap이 아닌 사업·재무·리스크 구조에서 근거를 도출
- 분할 매수 근거 — DCF 시나리오 가격대 기반으로 제시 (예: "Bear 수준 $120 이하에서 손익비 개선")
- 가장 취약한 숫자

### 7. 스트레스 테스트

**소스**: `{TICKER}_stress.md` 전체

> **리스크 요인(4번)과의 차이**: 리스크 요인은 DCF 시나리오 확률에 직접 반영된 위험이다. 스트레스 테스트는 DCF 가중평균에 반영하지 않는 외생 충격·꼬리 위험을 별도로 점검하는 참고 시뮬레이션이다.

stress.md의 내용을 그대로 가져오되, 동일한 모바일 가독성 규칙을 적용한다.

**구조:**

#### 7-1. 시나리오별 스트레스 테스트

stress.md의 각 시나리오를 그대로 포함한다. 시나리오 수를 줄이지 않는다.

각 시나리오에 포함할 내용 (stress.md 구조 동일):
- 가정
- 재무/밸류에이션 충격
- 버티는 근거
- 취약 근거
- 관찰 지표
- 실현가능성 (%) + 근거
- Bear DCF 반영 시 기여

충격 수치·실현가능성 등 짧은 값은 테이블로 정리해도 되지만, 가정·근거 등 문장 서술은 테이블 셀에 넣지 않는다.

#### 7-2. Bear DCF 시뮬레이션 합산

stress.md의 합산 테이블을 그대로 가져온다:

| # | 시나리오 | 충격 | 실현가능성 | Bear 기여 |
|---|---------|------|---------|---------|

테이블 아래에 동조성 해석(시나리오 간 상관관계)을 서술한다.

#### 7-3. Bear → Stress 반영 시 비교

stress.md의 비교 블록을 그대로 가져온다:
- 원본 Bear vs Stress 단순합산 vs 동조성 보정 vs Extreme Bear
- 시사점

**주의**: Revaluation 가중평균에는 반영하지 않는다는 점을 명시한다.

### 8. 모니터링 지표

**소스**: base 7번(모니터링 3개 테이블) + 8번(시나리오 진입 신호) + 9번(핵심 모니터링)

**합치는 원리**: 3곳에 분산된 모니터링 항목을 **1개 통합 테이블**로 합친다. 동일 지표가 다른 표현으로 반복되는 경우 1개로 합치되, 기준값·경고 기준·시나리오 연결을 모두 포함한다.

**중복 합침 예시** — "OCI 성장률"이 3곳에 등장:
- 7번 해자 모니터링: "OCI 매출 YoY 성장률 | 50%+ 유지 | ✓ (+84%)"
- 8번 Bear 진입 신호: "OCI 성장률 <50%"
- 9번 핵심 모니터링: "OCI 분기 성장률 (60%+ 유지 여부)"

→ app에서는 1개 항목으로 합침: "OCI 매출 YoY 성장률 | 기준 60%+ | 현재 +84% ✅ | <50% 시 Bear 진입"

**통합 테이블 구조:**

| 구분 | 모니터링 항목 | 기준값 | 현재 | 시나리오 연결 |
|------|------------|-------|------|-------------|
| 해자 | {항목} | {값} | ✅/⚠️ | {트리거 시나리오} |
| 리스크 | {항목} | {값} | | |
| 경쟁 | {항목} | {값} | | |

"시나리오 연결" 열은 base 8번의 시나리오 진입 신호에서 가져온다. 해당 기준값 돌파 시 어느 시나리오로 이동하는지 표시.

테이블 아래에 각 항목의 의미·맥락을 필요 시 서술한다.

**즉시 재검토 트리거**: base 7번의 트리거 목록을 그대로 포함한다.
